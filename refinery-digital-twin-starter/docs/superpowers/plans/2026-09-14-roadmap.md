# Refinery Digital Twin — Product Roadmap (Step 1: Tradeshow Presentation)

> **For agentic workers:** This is the master roadmap. It is NOT an executable task list. Each phase gets its own
> implementation plan written with `superpowers:writing-plans` at the start of that phase, saved next to this file
> as `YYYY-MM-DD-phase-N-<name>.md`. Phase 1's plan already exists: `2026-09-14-phase-1-silhouette-library.md`.
> Execute plans with `superpowers:subagent-driven-development` or `superpowers:executing-plans`.

**Goal:** Turn the synthetic-data refinery demo into a wow-factor interactive presentation where the equipment
shapes are true, the process is true, and the visuals are impressive — while keeping the architecture ready for
real (messy, anonymized) plant data later.

**Owner's framing (2026-09-14):** "Equipment has to be true, the process true, and visually impressive. Technical
accuracy and details can be de-emphasized. If the equipment on the outside matches the same shape, I am good. We
can never know the shape of the data now, so we work with what we have. We don't need exact specs — we strip the
identifiers and process back into our workflow."

**Non-negotiables from `AGENTS.md` that every phase must respect:** no hardcoded demo data in UI/3D logic; runtime
consumes only the canonical normalized model; every 3D asset has `asset_id`, `tag`, `type`, `unit_id`, `model_ref`;
deterministic naming (no `Cube.001`); synthetic data marked synthetic; generic capabilities, not one-off tricks;
offline/local runtime must keep working.

**Known defects to fix along the way (found in code review 2026-09-13):**
- `app/src/Scene.tsx` `Pipe`: `marker` ref is never attached — dead animation code. Flow animation is done by
  `FlowOverlay` on a raised arc that ignores the real `route_points`. (Phase 2)
- `evaluateScenario` `highlight_asset` pushes duplicates. Harmless. (Phase 3)
- Layer thresholds live in `operations.ts`, legend text duplicated in `main.tsx:58`. Layers should be data. (Phase 3)
- `BlenderAsset` clones every material per asset → 549 draw calls for 43 assets. (Phase 4)
- Code is written as very long one-liners (`main.tsx:60` is ~1,500 chars). Prettier pass is allowed but must be
  its own commit with zero behaviour change. (Any phase, when touching a file)

## 2. Working agreement (definition of done for every task in every phase)

1. `npm run check` passes (normalize, lint, vitest, pytest, validate, TypeScript, Vite build).
2. `npm run test:production` passes.
3. If geometry changed: `npm run check:generators` (Phase 1 adds it) and `npm run build:models` were run and the
   regenerated `data/normalized/models/refinery.glb`, `build-report.json`, and `blender/assets/refinery.blend` are
   committed.

   at project root (existing convention: `PHASE_0.md` … `PHASE_8.md`).
5. Commit per task with a conventional message; end commit messages with the attribution line the session provides.
6. Push to `main` at the end of each phase (or milestone) → verify the Pages deploy with
   `gh run watch <id> -R Mostafanasr1/refinery-digital-twin --exit-status` → open the live URL.
7. Windows/PowerShell: `&&` does not work in PowerShell 5.1. Use `;` or separate commands. `npm.cmd` works when
   `npm` is blocked by execution policy.

## 3. Phases

Order was chosen with the owner: **A → C → F → D → E → B** in the earlier discussion, i.e.
**1 Silhouettes → 2 Process truth → 3 Presentation → 4 Rendering foundation → 5 Visual pass → 6 Data interchange.**
Phases 1–5 need zero real data. Phase 6 is quick and has no visible payoff on the booth, so it is last, but it is
the first thing to run when the first client extract arrives.

| Phase | Name | Milestone (what the owner sees) | Est. |
|---|---|---|---|
| 1 | Silhouette library | 22 recognizable equipment types; the plant gains an LPG area and a hydrotreater | 1–2 wks |
| 2 | Process truth | Flow animates along real pipe routes; lines without routes get auto-routed along racks | 1–2 wks |
| 3 | Presentation layer | Guided cinematic tour with camera moves, captions, tweened values, idle attract mode, kiosk packaging | 2 wks |
| 4 | Rendering foundation | Same scene at ≤120 draw calls; 500-asset stress plant runs ≥60 fps on a laptop GPU | 1–2 wks |
| 5 | Visual pass | Baked lighting, PBR materials, HDRI sky, night mode, flare/steam, site context | 2–3 wks |
| 6 | Data interchange + anonymizer | Any equipment list + plot plan reduces to `essentials/` and round-trips through the pipeline with tags stripped | 1 wk |

### Phase 1 — Silhouette library ("equipment has to be true")

**Plan:** `2026-09-14-phase-1-silhouette-library.md` (complete, executable).

**Scope:** Refactor `equipment.py` into a `Kit` + `BUILDERS` registry; add `pipeline/catalog.py` as the single
source of truth for equipment types (tested against `schemas/asset.schema.json`); a Blender self-check script;
runtime proxy families; 12 new types: `floating_roof_tank`, `sphere_tank`, `bullet_tank`, `reactor`,
`horizontal_drum`, `air_cooler`, `compressor`, `cylindrical_heater`, `stack`, `hyperbolic_cooling_tower`,
`substation`, `control_room`. New synthetic units `unit_lpg` and `unit_hds` with 15 new assets.

**Acceptance:** `npm run check:generators` passes for all 22 types at detail 0 and 1; GLB test covers every asset;
the live site shows the new equipment; owner (ex-Enppi) confirms each silhouette reads as the right equipment.

**Design decisions:** Procedural from `dimensions` only (height/diameter/length/width) — this is the contract real
data must satisfy. One Blender `Kit` per asset; parts named `<model_ref>_<part>`; ≤ 6 materials total. No new
runtime features.

**Backlog for a Phase 1b (not planned yet):** loading rack, jetty/berth, boiler, blower/fan, filter, silo, tank
bund walls, pipe bridge, cable tray, road/fence primitives.

### Phase 2 — Process truth

**Scope:**
1. Delete the dead `marker` code in `Pipe`; move the flow animation from `FlowOverlay`'s raised arc onto the real
   `route_points` polyline (`THREE.TubeGeometry` along a `CatmullRomCurve3` of the route with `curveType:
   'centripetal'` and low tension, or straight segments with animated arrows). Keep `FlowOverlay` only as an
   explicit "explanatory" style selectable per path.
2. Auto-router: `pipeline/routing.py` — for a connection without `route_points`, route from the source nozzle
   (asset position + height 2.5) up to rack elevation, along the nearest `pipe_rack` axis, and down at the target.
   Grid A* on a 1 m plan grid where equipment footprints (from `dimensions`) are obstacles; rack corridors have
   zero cost. Writes `route_points` into the normalized output only (source stays untouched) and records
   `route_source: "generated"` on the connection. Validation: generated routes must not pass through any footprint.
3. Add a "Diesel Hydrotreating" process path over the Phase 1 HDS unit and a second scenario (heater trip → reactor
   quench) to prove the routing on new equipment.
4. `layerStyle` telemetry lookup indexed by `asset_id` in `AssetRegistry`.

**Acceptance:** every connection renders a pipe that ends at the equipment it connects; the trace animation follows
the pipes; a connection with no `route_points` in the source still renders a rack-following route; vitest asserts
routes never intersect a footprint.

### Phase 3 — Presentation layer

**Scope:**
1. Scenario engine v2 (`operations.ts`): `set_metric` gets optional `duration` and easing → values tween;
   `camera_move` action with `{position, target, duration, easing}`; `caption` action with `{text, duration}`;
   `highlight_asset` de-duplicates. Schema `scenario.schema.json` extended; validator checks `camera_move` targets
   exist. `evaluateScenario` stays pure in `seconds`.
2. Layers as data: `data/synthetic/layers.json` (`layer_id`, `parameter_match`, `range`, `palette`, `legend`);
   schema + loader + `layerStyle` reads it; delete the hardcoded thresholds and legend string.
3. Guided tour: a scenario `tour_reveal` implementing `docs/DEMO_STORYBOARD.md` scenes 0–4; "Follow the process"
   button starts it.
4. Idle attract mode: after 60 s without input, slow orbit + title; any input exits.
5. Kiosk: `?kiosk=1` hides chrome, fullscreen API, larger hit targets, touch tuning for OrbitControls.
6. Packaging: Tauri (or Electron) wrapper around `scripts/serve.mjs` + `app/dist` producing a Windows installer
   that runs offline. Document in `docs/KIOSK.md`.
7. State store: move `Explorer` state to a zustand store (`app/src/store.ts`) so `Scene` subscribes to slices.

**Acceptance:** presenter presses one button and a 3–5 minute narrated (captions) tour runs unattended; the same
build runs from a USB stick without network.

### Phase 4 — Rendering foundation

**Scope:**
1. Shared materials: stop cloning materials in `BlenderAsset`; tint/dim/active via a per-object uniform injected
   with `material.onBeforeCompile` or a vertex-color attribute; selection outline via a postprocessing outline
   pass (from `postprocessing` npm package) instead of emissive changes.
2. Instancing: assets of the same `type` **and** equal `dimensions` share one `InstancedMesh` per part mesh
   (GLB export keeps one mesh per part; runtime groups by `model_ref` geometry hash).
3. `three-mesh-bvh` for raycast picking.
4. `gltf-transform` post-step in `scripts/build_models.py`: weld, dedupe, meshopt compress, quantize. Runtime
   registers `MeshoptDecoder`. Target: `refinery.glb` ≤ 2 MB.
5. LOD: build GLB at `--detail 0` too (`refinery.lod0.glb`); runtime swaps by camera distance using `THREE.LOD`.
6. Stress test: `scripts/stress_plant.py` generates a 500-asset synthetic plant into a temp dir; measure fps and
   draw calls via the `data-performance` attribute `Atmosphere.tsx` already writes.

**Acceptance:** 43-asset plant ≤ 120 draw calls; 500-asset stress plant ≥ 60 fps at 1080p on an integrated laptop
GPU; GLB ≤ 2 MB; picking latency unchanged.

### Phase 5 — Visual pass

**Scope:**
1. Blender: bake AO (and optionally a sun lightmap) to a second UV set per asset; export as KTX2 textures.
2. Triplanar PBR materials (albedo/roughness/normal) for steel, painted steel, concrete, insulation; ≤ 8 material
   families; texture atlas ≤ 16 MB.
3. Environment: HDRI sky (CC0 from Poly Haven — ask the owner before downloading; ~5 MB each) with matched
   directional sun; time-of-day slider; night mode with emissive lamps.
4. Post stack via `postprocessing`: GTAO, TAA/SMAA, bloom (existing), colour-grading LUT, optional DoF for tour
   shots.
5. Effects: flare flame (shader/particles on `flare` tip), stack steam, cooling-tower plume.
6. Site context: ground plane with roads, bund walls around tank groups (derived from tank positions), fence,
   lighting masts, a few vehicles for scale. All generated from data (unit footprints), not hand-placed.

**Acceptance:** side-by-side before/after screenshots at three tour shots; owner signs off on "looks premium";
frame rate within 15% of Phase 4 numbers.

### Phase 6 — Essentials interchange + anonymizer

**Scope:**
1. `docs/ESSENTIALS.md`: the minimum-truth contract — three tables (equipment, lines, units) with required and
   optional columns. Equipment: tag, type, height, diameter, length, width, x, y, z, rotation, unit. Lines: from,
   to, service, size, optional waypoints. Units: id, name, area.
2. `pipeline/essentials/adapters/xlsx.py`: Excel/CSV → essentials JSON with a column-mapping file.
3. `pipeline/essentials/anonymize.py`: keyed tag remap (`identity_map.csv` written next to the output, never
   committed — add to `.gitignore`), coordinate rebase to plant-local origin, drop every column not in the
   contract. `pipeline/essentials/to_canonical.py`: essentials → `data/<client>/` synthetic-format JSON with
   `synthetic: false` support (schema change: `synthetic` becomes boolean).
4. Runtime: optional `identity_map.json` loaded from `?identity=` URL or local file picker to re-attach real tags
   on the booth machine only.
5. Tolerance: `AssetRegistry` must not throw on a missing binding — assets without geometry fall back to the proxy
   family; a data-quality panel lists unresolved items.
6. Spec (not runnable here): `docs/NAVISWORKS_EXTRACT.md` describing the C# .NET plugin that dumps tag, category,
   bounding box, centroid, rotation per ModelItem to essentials CSV.

**Acceptance:** the synthetic plant exported to Excel, anonymized, and re-imported produces an identical demo with
different tags; a deliberately messy sheet (duplicate tags, missing dimensions, unknown types) imports with a
quality report instead of a crash.
